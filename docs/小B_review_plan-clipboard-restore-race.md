Confirmed OK:

- The premise matches the code and `435aa79`. 1.3.3 did not change the 50ms or 200ms waits. It made restore the default (`useSettingsStore.ts:82`, one-shot migration at `useSettingsStore.ts:485-501`) and restore via `clearContents` plus full-type write (`clipboard_paste.rs:464-516`). The green check is `await invoke("paste_text")` then `transitionTo("success")` (`useVoiceFlowStore.ts:814-819`). It means the command returned `Ok`, not that the target pasted. Turning restore off is a real ablation of this race. Leaving the four `CGEvent`s and the 50ms post-write sleep alone is justified.
- Tauri 2.10.2 sync commands run on the main thread. `AppHandle::run_on_main_thread` is safe from a detached sleeper, including when the HUD is hidden and the policy is Accessory. This app already hops to the main thread for that policy (`lib.rs:160-180`). Do not block the main thread waiting for the closure. The sleeper must not hold `PENDING_RESTORE` across that hop (deadlock if the closure needs the same mutex).
- `NSPasteboard.changeCount` increments on ownership and content changes (`clearContents`, `writeObjects`, `setString:forType:`), not on read. arboard 3.6.1 `set_text` is `clearContents` then `writeObjects` of an `NSString` (eager, not a promise), so sample the sequence after `set_text` returns. Read-only history apps (typical Maccy, Raycast, Alfred, Paste) do not bump it, so the guard still restores for the reported setup. A manager or Universal Clipboard that writes back skips restore and leaves the transcript. That direction is acceptable.
- `GetClipboardSequenceNumber` is in `windows` 0.61.3 at `windows::Win32::System::DataExchange`, feature `Win32_System_DataExchange` (depends only on `Win32_System`). Adding that feature does not add a crate, so `Cargo.lock` stays unchanged. It is not main-thread-affine. `OpenClipboard` is one opener at a time, and `CloseClipboard` must run on the opening thread.
- Back-to-back reuse is right: if the sequence is still `pending.written_seq`, snapshot the pre-transcript contents, not the previous transcript. If it differs, drop `pending` and snapshot whatever is there now. Two atomic main-thread calls (whole `paste_text`, or whole restore closure) do not need a special interleaving beyond the HIGH rule. `copy_to_clipboard` (History, Settings) is covered by the sequence check.
- App exit during the window should be accepted. A detached `std::thread` is killed when the process exits and does not delay quit. Restoring in `RunEvent::Exit` can put the old clipboard back before a slow target reads, which recreates the bug on quit or updater restart. A leftover transcript is the same outcome as restore off.
- IPC stays `paste_text(text, restoreClipboard)`. The frontend does not call `read_selected_text` anymore. `capture_selected_text_via_clipboard` can stay out of scope.
