**Confirmed OK**

- **The accepted diagnosis warrants a focused restoration fix.** Commit `435aa79` changed the default/migration and snapshot restoration without changing the 50ms/200ms delays. The current frontend passes `restoreClipboard: !isCopyTranscriptionToClipboardEnabled`. I agree with leaving keyboard-event construction and focus handling outside this patch.

- **A remains the best fit if clipboard preservation and prompt completion are requirements.** B alone prolongs blocking and still overwrites intervening copies. C is the simplest workaround when preservation is optional. D adds complexity without a consumption acknowledgement. The existing Tokio time dependency also makes an async timer available without adding a dependency (`src-tauri/Cargo.toml:32`); a sleeping thread is acceptable but unnecessary.

- **The main-thread premise is supported for the current desktop invocation path.** The lockfile pins Tauri 2.10.2, macros 2.5.4, runtime-wry 2.10.0, and Wry 0.54.2 (`src-tauri/Cargo.lock:5937,6039,6292,8030`). The synchronous wrapper directly invokes the command, consistent with [Tauri’s documented execution model](https://v2.tauri.app/develop/calling-rust/) and [the matching macro source](https://raw.githubusercontent.com/tauri-apps/tauri/tauri-v2.10.2/crates/tauri-macros/src/command/wrapper.rs). Ordinary command dispatch and a main-thread restoration closure therefore serialize; the command macro itself is not a main-thread dispatcher for arbitrary Rust callers.

- **Dispatching restoration from a worker is supported.** Runtime-wry sends a task to the event loop when called off-thread, with no window-visibility condition in that path. Do not hold the pending mutex while waiting for dispatch or completion. Hidden-HUD/Accessory behavior still needs the planned runtime test. [Runtime source](https://raw.githubusercontent.com/tauri-apps/tauri/tauri-v2.10.2/crates/tauri-runtime-wry/src/lib.rs).

- **Keeping native clipboard work on the main thread is a sound choice.** Transfer owned snapshots and generation IDs, not Objective-C objects or an open Win32 clipboard guard. Windows arboard’s `Clipboard` object does not hold the clipboard open; each operation acquires/releases it, and its open guard cannot cross threads. Creating a fresh handle in the restore closure is appropriate. [Arboard source](https://raw.githubusercontent.com/1Password/arboard/v3.6.1/src/platform/windows.rs).

- **Passive history reads do not themselves transfer macOS pasteboard ownership.** Apple defines `changeCount` around ownership changes, not every possible data mutation. Managers can write: Maccy’s history-selection operations clear/repopulate the pasteboard, whereas its polling path reads it. Skipping restoration after such a write is the correct conservative outcome. This does not establish the behavior of the user’s unnamed manager or its extensions. [Apple](https://developer.apple.com/documentation/appkit/nspasteboard/changecount), [Maccy source](https://raw.githubusercontent.com/p0deje/Maccy/master/Maccy/Clipboard.swift).

- **The Windows feature addition should not change this lockfile.** The exact 0.61.3 manifest defines `Win32_System_DataExchange = ["Win32_System"]`, introducing no package dependency; the parent feature is already enabled through existing features. The expected symbol is `windows::Win32::System::DataExchange::GetClipboardSequenceNumber`, returning `u32`. I verified the exact feature manifest and Microsoft’s published symbol documentation, but could not retrieve the 0.61.3 symbol source or compile it here; keep the Windows build as the final binding check. Feature changes can affect lockfiles when they activate dependencies, so the plan’s blanket explanation is too broad. [0.61.3 manifest](https://docs.rs/crate/windows/0.61.3/source/Cargo.toml), [Microsoft binding documentation](https://microsoft.github.io/windows-docs-rs/doc/windows/Win32/System/DataExchange/fn.GetClipboardSequenceNumber.html).

- **Accepting pending restoration loss on exit is reasonable for this patch.** Do not add unconditional early restoration in `RunEvent::Exit`: that can recreate the same race immediately before quitting. The existing exit handler blocks during cleanup and ultimately calls `_exit`, so a queued restoration cannot be assumed to execute (`src-tauri/src/lib.rs:811–870`). Document the limitation and test quit/restart during the window.
