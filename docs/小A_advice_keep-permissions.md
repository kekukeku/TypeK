## 二、 為什麼「其他 App」更新後能保留權限，而 TypeK 不行？

1. **商業/正式 macOS 應用程式的做法：**
   - 絕大多數支援自動更新的 App 都擁有付費的 **Apple Developer ID** 憑證。
   - macOS TCC（隱私權控制中心）認定應用程式身份並不是只看檔名或路徑，而是比對該程式的 **Designated Requirement (DR，指定需求)**。
   - 擁有 Developer ID 的程式，其 DR 格式為：  
     `designated => identifier "com.xxx.app" and anchor apple generic and certificate leaf[subject.OU] = TEAM_ID`
   - 不管軟體更新升級多少次、執行檔二進位雜湊（cdhash）如何改變，只要 **Team ID** 與 **Bundle ID** 不變，macOS 便認定這是「同一個信任主體」，因此隱私權限（輔助使用、麥克風、輸入監控等）可以跨版本無縫保留。

2. **TypeK 目前的困境（Ad-hoc 簽名）：**
   - TypeK 目前設定為 `signingIdentity: "-"`（ad-hoc 臨時簽名）。
   - ad-hoc 簽名的 DR 強制綁死在二進位檔案的特定雜湊值：  
     `designated => cdhash H"99efb3f175cc92036dfbce86950119fc6a91090e"`
   - 只要任何一次更新（無論是 DMG 覆蓋或 1.3.0 引入的 in-app 自動更新），二進位內容改變，**cdhash 就必定改變**。
   - 系統設定介面中看到的 TypeK 雖然仍為「開啟（ON）」，但那是系統紀錄的「上一版 cdhash 舊紀錄（Stale Record）」；底層 API `AXIsProcessTrusted()` 檢驗當前執行的二進位檔時回傳 `false`，全域快捷鍵與按鍵監聽隨即中斷。

## 三、 技術選項簡評（在不付費 Apple 帳號的前提下）

### 1. 方案 A：GitHub CI 導入長期自簽代碼簽名憑證（技術推薦）
- **原理機制**：
  在 macOS 系統中，TCC 檢查 DR 時，**只關心 cryptographic match（密碼學比對是否相符），而不強制要求憑證必須向 Apple 官方 CA 鏈結節點背書**。
  如果我們使用同一張自簽程式碼簽署憑證簽發每次 Release，產生的 DR 將變為：
  ```text
  designated => identifier "com.kekukeku.typek" and certificate leaf = H"<固定憑證公鑰指紋>"
  ```
  如此一來，跨版本的更新包擁有完全相同的憑證 leaf 雜湊，macOS TCC 即可直接繼承授權。開源專案（如 trycua/cua PR #1792）已驗證此機制在 macOS 上可行。
- **優缺點分析**：
  - **優點**：完全免費（0 元），一旦生效，使用者後續每一次自動更新將徹底告別「權限失效」問題。
  - **限制**：因未經過 Apple 公證（Notarization），使用者第一次下載打開時，依然需要點右鍵開啟或到系統設定「強制打開」（此點與現狀 ad-hoc 完全相同，並未惡化）。
- **建議**：後續可由工程團隊在 CI 嘗試導入驗證；若順利通過，即能以最小代價達到商業級 App 的更新體驗。

### 2. 方案 B：App 內「一鍵重設權限（tccutil reset）」可行性分析
- **評估結論：不可行，強烈建議放棄此念頭。**
- **不可行原因**：
  1. **系統權限阻擋**：macOS 為了防止惡意軟體無限騷擾使用者，嚴禁一般應用程式未經授權在背景擅自呼叫 `/usr/bin/tccutil` 修改自身或全域的 TCC 資料庫。在 macOS 14 / macOS 27 環境下，此類呼叫多會直接失敗或被 sandbox 機制拋棄。
  2. **流程半套與反效果**：`tccutil reset Accessibility com.kekukeku.typek` 的功能是**將該列從資料庫徹底抹除**。它無法幫使用者把新版程式加回去。若清空後，使用者到設定面板只會發現 TypeK 完全消失，還必須自己點擊「+」在檔案瀏覽器裡層層尋找 `/Applications/TypeK.app`，非技術使用者的操作門檻反而大幅飆升。
- **適當定位**：提供「複製指令」作為折疊式的高級排錯手段，而不做成一鍵按鈕。

## 四、 面向非技術使用者的平滑 UX 體驗設計（三階段全生命週期）

假設在 ad-hoc 限制無法立刻根治的現狀下，UX 設計必須為非技術使用者抹平技術瑕疵，打造最低認知負擔的「更新閉環」。

```
【更新準備】
發現更新 → 提示更新內容 + 心理預備（提醒更新後可能需重新整理權限）
   ↓
【安裝重啟】
點擊安裝並重啟 → 自動啟動新版 TypeK
   ↓
【版本感知】
TypeK 偵測到「版本剛升級」且「權限失效」
   ↓
【友善引導（非報錯）】
彈出引導：「歡迎使用新版本！最後一步：快速啟用快捷鍵」
   ↓
【操作閉環】
點擊「前往設定」直達面板 → 引導簡易「− 再 +」→ 系統偵測成功 → 提示「重新啟動 TypeK」
```

---

### 階段一：更新安裝前（心理預期管理）

非技術使用者遇到問題最大的恐懼來自「無預警的失效」。如果在點擊更新前就告知「更新後需要重新確認」，使用者的心理抗拒會降低 80%。

#### 1. 自動更新就緒提示（Auto-Update Dialog）
- **位置**：`src/MainApp.vue` 中的自動更新對話框。
- **UX 改良點**：
  - 在「安裝並重啟」按鈕上方，增加一塊醒目的輕量資訊卡片（藍色或灰色提示底色，非刺眼的紅黃色錯誤）。
  - **文案**：
    > **更新提示**：  
    > 為確保快捷鍵正常運作，macOS 在應用程式更新後可能需要重新確認一次權限。更新完成後 TypeK 會一步步引導你，只需 10 秒即可搞定。
  - **按鈕**：`[ 稍後提醒 ]` 與 `[ 立即安裝並重啟 ]`。

---

### 阶段二：重啟後第一時間（情境感知與非報錯式溝通）

#### 1. 避免誤診：區分「首次安裝」與「更新後權限過期」
目前 TypeK 無論任何情況只要 `AXIsProcessTrusted() == false`，就會彈出冷冰冰的「需要輔助使用權限」警告視窗。非技術使用者看到開關明明是開的，會認定軟體「壞掉了」。

- **前端狀態記錄（Context-Aware State）**：
  - 在前端儲存鍵值：`lastActiveVersion`。
  - 若 `currentVersion !== lastActiveVersion` 且 `AXIsProcessTrusted() == false`，介面進入 **「更新專屬重新整理模式（Stale Grant Flow）」**，而不是常規的初次授權模式。

#### 2. 視窗氛圍改造
- **視覺圖示**：由原本的警示盾牌（Warning Shield）調整為帶有打勾與重新整理箭頭的柔和圖示（如 Shield-Sync 或 Sparkle-Key），降低警報焦慮。
- **核心話術**：
  - **標題**：`歡迎使用 TypeK v{version}！`
  - **副標題**：`還差最後一步：為新版本啟用快捷鍵權限`
  - **真相說明（一句話破解盲點）**：  
    > *「macOS 隱私機制會將更新版本視為新程式。如果設定中的開關已經開啟，只需『先移除、再重新加入』即可恢復。」*

---

### 階段三：AccessibilityGuide 介面重構（逐步引導與雙按鈕閉環）

#### 1. 精準路徑導航（macOS 27 與舊版相容）
目前程式內的深連結網址為 macOS 12 時代的舊網址：  
`x-apple.systempreferences:com.apple.preference.security?Privacy_Accessibility`

- **改進建議**：
  - 優先開啟現代 macOS / macOS 27 正確的「裝置控制與資料存取」錨點：  
    `x-apple.systempreferences:com.apple.settings.PrivacySecurity.extension?Privacy_Accessibility`
  - 文案特別標明：  
    **「系統設定 → 隱私權與安全性 → 裝置控制與資料存取（舊版系統稱為輔助使用）」**，避免使用者迷航到側邊欄的輔助使用（縮放/旁白）。

#### 2. 三步驟白話引導清單（圖文搭配）
1. **第一步：開啟設定**  
   點擊下方按鈕，系統將自動開啟隱私設定面板。
2. **第二步：重新整理清單**  
   在列表中找到 **TypeK**，點擊下方的 **「 − 」** 移除；接著點擊 **「 + 」**，從應用程式資料夾重新選取 **TypeK** 並開啟開關。  
   *(提示：如果開關已經是開啟狀態，必須先移除再加入才有效)*
3. **第三步：回到 TypeK**  
   授權完成後，點擊下方「重新啟動 TypeK」，快捷鍵立即生效。

#### 3. 按鈕佈局與互動反饋設計

介面提供極簡的兩顆主要按鈕，並配合背景輪詢（Polling）實現狀態連動：

```
+-------------------------------------------------------+
|  [ ↗ 開啟系統隱私設定 ]   (點擊後直達設定頁面)          |
+-------------------------------------------------------+
|  [ 🔄 重新啟動 TypeK ]     (常態次要，權限通過時變高亮)   |
+-------------------------------------------------------+
|   稍後手動設定            進階終端機指令 ▾             |
+-------------------------------------------------------+
```

- **按鈕 1：`[ ↗ 開啟系統隱私設定 ]`（主要動作）**
  - 點擊後喚醒系統設定並直接定位到對應面板。
- **按鈕 2：`[ 🔄 重新啟動 TypeK ]`（關鍵閉環動作）**
  - **背景即時偵測**：前景以每 1.5 秒輪詢 `check_accessibility_permission_command`。
  - **動態狀態轉變**：
    - 當偵測到 `AXIsProcessTrusted() == true`：
      - 介面上方立即切換為綠色成功反饋：`✓ 權限已成功更新！`
      - 「開啟系統隱私設定」按鈕淡出或轉為次要。
      - 「重新啟動 TypeK」按鈕自動亮起（變為高亮綠色/強調色），提示文字：`立即重啟以啟用快捷鍵`。
      - 點擊後直接調用既有的重啟指令，確保 Event Tap 在乾淨的行程狀態下建立。
- **輔助項目**：
  - **`稍後設定`**：使用者可跳過。跳過後，在主視窗頂部或右上角選單列保留一個小黃點提示，點擊可再次呼出此引導。
  - **`進階排錯（折疊式）`**：點擊展開顯示：*「快捷鍵依然沒反應？點此複製終端機指令 `tccutil reset Accessibility com.kekukeku.typek`」*，點擊自動複製至剪貼簿並彈出 Toast。
